# Implementation Plan: el-storko — Personal Work-Item Tracker

**Branch**: `001-el-storko` | **Date**: 2026-09-21 | **Spec**: [wiki/specs/001-el-storko/spec.md](../../specs/001-el-storko/spec.md)

**Input**: Feature specification from `wiki/specs/001-el-storko/spec.md`

## Summary

A single-user, always-on work-item tracker that unifies ad hoc personal Tasks/Epics with
Jira issues assigned to the user, bidirectionally synced by polling, and leaves a `source`
field ready for a future AI-agent producer. Delivered as a Go+Postgres backend
(`backend/el-storko/`), a Next.js zone (`apps/el-storko/`), and a thin Go CLI, all against
one REST API and one database, matching this repo's existing `oncarinho` conventions.

## Technical Context

**Language/Version**: Go 1.22 (backend + CLI), TypeScript/Next.js 14 (frontend)

**Primary Dependencies**: Gin (HTTP), golang-migrate (migrations), `lib/pq` or `pgx` (Postgres driver, matching oncarinho's existing choice), Jira REST API v3 client (hand-rolled HTTP client — no heavyweight SDK), Next.js 14 App Router, `@movoz/theme`, `@movoz/tailwind-config`, `@movoz/tsconfig`

**Storage**: PostgreSQL (`el_storko` database), single `work_items` table

**Testing**: `go test ./...` for backend/CLI (store + handler tests per resource, matching oncarinho); no frontend test suite exists elsewhere in the repo, so manual verification via `pnpm --filter el-storko dev` matches project convention

**Target Platform**: macOS, local-only (localhost-bound), always-on via launchd

**Project Type**: Web application (Go backend + Next.js frontend + Go CLI, three deliverables sharing one API/DB)

**Performance Goals**: Not a performance-sensitive system — single user, low request volume; no specific targets beyond "feels instant" for CRUD operations

**Constraints**: Jira token never logged/committed/returned by any API response; sync interval is poll-based (Jira cannot reach an unexposed local service); service must survive reboot/crash unattended

**Scale/Scope**: Single user, expected tens to low hundreds of work items; two-level hierarchy (Epic → Task) only

**Structure Decision**: Web application layout (Option 2 shape), adapted to this repo's
existing `backend/<service>/` + `apps/<zone>/` split rather than generic `backend/`/`frontend/`
directories — matching `oncarinho`. A third deliverable (`cmd/cli/`) lives inside the same Go
module as the server so it shares `internal/models` and hits the same REST API, avoiding
duplicated business logic per FR-010.
